# 브리프 01: core-platform (공통 플랫폼)

## 목적
모든 대기 자원을 하나의 모델로 저장하고, 통합 대시보드에서 실시간 상태와 예상 대기시간을 보여준다. 다른 스펙은 이 플랫폼 위에 어댑터로 붙는다.

## 사용자 스토리
- 학생으로서, 한 화면에서 세탁실·학식·셔틀의 현재 상태와 예상 대기시간을 보고 싶다. 어디로 먼저 갈지 정하기 위해서다.
- 학생으로서, 로그인 없이 바로 쓰고 싶다.
- 학생으로서, 표시된 값이 실측인지 예측인지 알고 싶다.
- 학생으로서, 줄 길이를 한 번의 탭으로 제보하고 싶다.

## 요구사항 초안 (EARS)
- REQ-CORE-01: 시스템은 resource(kind, zone, name, capacity, source)를 저장하고 kind별로 조회할 수 있어야 한다.
- REQ-CORE-02: WHEN 사용자가 앱을 처음 열면, 시스템은 익명 기기 ID를 생성해 기기에 보관해야 한다.
- REQ-CORE-03: WHEN 자원의 상태가 갱신되면, 시스템은 10초 이내에 열려 있는 대시보드에 반영해야 한다.
- REQ-CORE-04: 시스템은 각 자원 카드에 상태, 예상 대기시간, 데이터 출처(실측·제보·예측), 마지막 갱신 시각을 표시해야 한다.
- REQ-CORE-05: IF 영상 데이터가 60초 이상 없거나 confidence가 기준값 미만이면, THEN 시스템은 최근 15분 제보 또는 예측값을 표시하고 출처를 바꿔 표시해야 한다.
- REQ-RPT-01: IF 한 기기가 같은 자원에 10분 안에 두 번째 제보를 보내면, THEN 시스템은 제보를 거부하고 재제보 가능 시각을 안내해야 한다.
- REQ-RPT-02: 시스템은 30분이 지난 제보를 현재 상태 계산에서 제외해야 한다.
- REQ-SYS-01: 시스템은 사용자의 학번, 이름, 위치 좌표를 저장하지 않아야 한다.
- REQ-SYS-02: 시스템은 모든 테이블에 RLS를 적용해, 익명 사용자가 다른 기기의 대기표·구독 정보를 읽거나 수정할 수 없게 해야 한다.

## 데이터
`resources`, `status_events`, `reports`, `push_subs`, 그리고 다른 스펙이 쓸 `vision_metrics`, `queue_tickets`, `predictions`의 기본 형태.

## 범위 밖
로그인, 결제, GPS, 관리자 권한 체계(05-extras에서 다룸).

## 완료 기준
시드 데이터 자원 5개가 대시보드에 보이고, DB 값을 바꾸면 10초 안에 화면이 바뀐다. 제보 빈도 제한 테스트가 통과한다.
